# 角色现金收购统计（V1.8.0）

## 业务口径

以登录主机账号下的游戏账号 ID 为唯一角色键（不是昵称、窗口 HWND 或从机编号）。在已确认的连续现金观测中，增加视作资金账号补入，减少视作宝石收购支出。只统计现金，不把存银算作可收购本金；无法识别账号 ID 时不记账。

例：起始 10000000，补入 10000000，结束 3000000，则收购支出为 **17000000（1700 万）**，不是 170000000。

每次现金变化在从机连续三帧确认后立即记录、顺序上报，未改变的金额每 5 秒记录一个覆盖心跳；新自然小时强制上报。不能仅依赖原有 5 秒状态快照，否则期间先补款、再支出的两次变化可能丢失。

金额流使用持久化本地发件队列及服务端唯一事件 ID 去重；服务端串行事务更新累计值，防止重传重复记账、并发丢失更新。账号 ID 一致时昵称变化只更新展示文字；切换窗口或设备重建监控基线，旧记录仍归入同一 ID。

## 监控中断

用户已确认：暂停、关闭程序、关闭背包、无法识别现金、最小化、连接被判断离线时结束当前连续段；恢复后第一个确认金额作为新基线，不计算跨中断的补款或支出。客户端/服务端 15 秒无有效现金观测也会重建基线，避免异常退出或采集停止后跨空白时段计算。

正在等待金额变化的第三帧确认、但数字仍清楚可读时不视为中断。现金确认独立于存银，存银不可读不阻止现金记账。

每日起始金额是该日最早统计段的起始余额，结束金额是最后确认余额。有中断时，不能只用起始+补款-结束算支出，界面另显示“未监控净变动”作为未计入收购/补款的余额差。公式为：

`收购支出 = 起始金额 + 补入金额 + 未监控净变动 - 结束金额`

例如起始 1000→900（收购100），中断，恢复2000→1800（收购200），当天收购300、补入0、未监控净变动+1100。

## 自然小时与自然日

固定使用北京时间 Asia/Shanghai（UTC+8）。现金增减按**连续监控中被确认的时刻**归属自然小时；跨小时仍连续时，以上一小时最后已知余额作为新小时起始，跨日相同。这是基于观测时间的统计，不能还原两个采样点之间真实交易发生在哪一侧的精确时刻。

监控覆盖秒数按观测间隔分摊到各自然小时。持续全天监控时生成 24 个小时行；完全未观测的小时不创建记录，而非补为零收购。中断小时只累计其已监控片段。第一笔基线没有已知覆盖时长。

主机新增“游戏币统计”页，支持日期、账号 ID 筛选，展示每日和每小时起始、补入、收购、结束、未监控净变动、覆盖时长；当天视图跨午夜自动跟随新日期，历史日期不自动跳走。新主机账号配置会清空旧账号展示，并拒绝旧登录请求的统计响应。

## 精度边界

若两次成功识别之间同时发生补入和收购，余额只能给出净变化，无法从余额还原各笔交易；界面明确显示此限制。不能通过此方案识别补款人的账号 ID，亦不能推算宝石数量或品种。识别错误持续通过三帧也可能影响账目；应保留真实截图回归测试并核对关键余额。

## 新接口与持久化

- `POST /api/v1/slave/cash-observations`：账号 ID、流 ID、顺序号、带时区时间、现金或结束标记。鉴权决定主机账号，不能跨账号写入。
- `GET /api/v1/master/cash-statistics?day=2026-10-20`：返回 daily/hourly。鉴权隔离主机账号。
- SQLite 新增 cash_observations、cash_states、cash_hours，增量创建，不改旧记录。
- 同角色的不同连续流（包括重复窗口和跨设备）同时上报时，15 秒内保留现有连续来源，冲突来源不计入；旧时间和乱序事件不改账。

V1.8.0 开始提供此功能，服务端须为 2.5.0 或更新版本；历史 V1.7.1 余额快照无法补算此前未留存的逐笔现金变化。手机 H5 本次未增加统计界面。

## 验证

业务例子、暂停恢复与长时间失联、重复和乱序重传、跨账号隔离、账号 ID 更名归并、服务端重启恢复、北京时间跨日/跨小时、无监控小时不补零、整日 24 个小时记录和覆盖时长均有自动化验证。源端覆盖变化即时记录、未确认候选不误断线、离线/不可读断段、小时心跳、旧队列帧不重开监控；发件队列验证重启后仍走现金接口，且确认后清除。

最终检查：客户端分组 10+21+14+114=159 项通过，服务端 22 项通过。V1.8.0 发布时先备份并部署服务端，再签名发布客户端。
