# 05. 模型选型：YOLO、OCR 与视觉大模型

## 1. 是否必须使用视觉大模型

**第一版不需要。**

游戏界面通常具有固定的窗口布局、固定的按钮位置和相对稳定的字体。对于这些任务，专用的小模型和规则更适合：

- YOLO：检测面板、按钮、战斗标志、技能图标、物品格。
- OCR：读取地图名、物品名、技能名和伤害数值。
- 模板匹配：识别固定图标和固定 UI。
- 像素差分：发现某个 ROI 是否发生变化。
- 状态机：根据时间顺序理解“打开、进入、结束”。

视觉大模型可能更通用，但通常存在延迟、成本、结果不稳定和难以严格复现的问题。它不适合作为每一帧的默认推理器。

## 2. YOLO 负责什么

YOLO 解决的是目标检测：

```text
输入图片 → 类别、边界框、置信度
```

适合训练的类别示例：

```text
inventory_panel
battle_panel
skill_icon
map_name_region
item_slot
chat_panel
mission_button
```

不建议把每一个物品名称都直接作为 YOLO 类别，类别会迅速膨胀。物品名称更适合由“物品格检测/定位 + OCR 或图标分类”完成。

## 3. OCR 负责什么

OCR 读取文字内容：

- 地图名称。
- 背包物品名和数量。
- 技能名称。
- 战斗日志。
- 伤害数字。

OCR 前应先做 ROI 裁剪和预处理，整屏 OCR 往往会带来大量误识别和额外耗时。

## 4. 其他模型的适用位置

| 任务 | 首选 | 何时增加模型 |
|---|---|---|
| 固定按钮是否出现 | 模板/像素规则 | UI 有多套皮肤时用 YOLO |
| 面板定位 | YOLO | 画面布局变化大时增加分类器 |
| 地图场景分类 | 轻量分类模型/规则 | 地图画面差异小且 OCR 不可靠时 |
| 物品图标识别 | 分类模型/感知哈希 | 物品样式很多且无文字时 |
| 技能释放判定 | ROI 变化 + OCR + 状态机 | 动画复杂时再训练时序模型 |
| 全屏开放域理解 | 视觉大模型 | 低频人工复核或未知画面兜底 |

## 5. 视觉大模型的正确位置

可以作为**低频、非实时、可选的兜底层**：

1. 当专用模型置信度低时，抽一张证据帧请求视觉大模型解释。
2. 对未知弹窗进行分类，帮助人工建立新规则。
3. 对已生成的结构化事件做自然语言总结。
4. 辅助标注数据和发现漏标类别。
5. 离线分析整段视频中的高层摘要。

不要让视觉大模型直接输出未经校验的键盘鼠标动作，也不要让它替代确定性的白名单、状态机和安全规则。

## 6. 是否需要“hoyo”

当前软件对外名称是 **“梦幻西游-希联文超助手”**。代码中的 `hoyo` 只是早期遗留的内部包名，不是模型类型，也不是必须安装的软件。真正需要的技术组件是：

```text
FFmpeg/OpenCV + NumPy + YOLO + OCR + Python 状态机 + JSONL/SQLite
```

如果你说的“hoyo”特指某个已有 SDK、标注平台或视觉框架，需要提供它的准确名称或链接；否则本方案不把它当作外部依赖。

## 7. 推荐的模型落地顺序

```text
第 1 版：模板匹配 + ROI OCR + 状态机
第 2 版：YOLO 检测固定 UI 和关键图标
第 3 版：物品/技能图标分类与 OCR 融合
第 4 版：轻量场景分类和时序稳定模型
第 5 版：视觉大模型作为低频兜底与离线总结
```

这样可以先验证数据闭环，而不是先花大量时间训练一个无法解释的“大一统模型”。
